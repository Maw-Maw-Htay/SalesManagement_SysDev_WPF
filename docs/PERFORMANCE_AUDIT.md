# 販売在庫管理システムの性能監査

## 測定条件

WPF／.NET 8、EF Core 7.0.20、SQL Server 2019 LocalDB 15.0.4382.1。変更前の作業ツリーから作成済みのアプリと、今回の変更後のアプリを、同じシードデータの専用 LocalDB インスタンスで比較した。履歴は受注2,400件と社員600件、注文と売上は各1,200件、明細は1伝票当たり最大6行。履歴は3ページ目の20件を取得した。SQLは EF Core のコマンド完了イベントを数え、経過時間はウォームアップ後15回の中央値を比較した。ログインは WPF の `Loaded` ハンドラーが制御を返す時点と、接続結果が表示できる時点を各3回測定した。

テストデータの書き込みは検証専用カタログで行った。計測環境の LocalDB と実運用ではデータ分布、メモリ、入出力の待ち時間が異なる。

| 注文一覧・営業 | 2 → 1 | 188.6 ms | 46.8 ms |
| 売上一覧・管理者 | 6 → 4 | 59.1 ms | 55.9 ms |
| 売上一覧・営業 | 6 → 4 | 47.4 ms | 44.6 ms |

| 履歴の社員タブ | 5 → 4 | 93.2 ms | 65.8 ms |

- ログインは接続失敗時に画面へ制御を返すまでの待ち時間が短くなった。接続完了自体の待ち時間は計測上短縮しなかった。
- 変更前の注文一覧は別の試行でSQL Serverのメモリ許可待ち `RESOURCE_SEMAPHORE` が発生した。表には待ちが観測されなかった試行を採用した。全件履歴や売上の軽微な時間差には実行ごとの変動が含まれる。
- 顧客・商品は45件選択時の `SelectedCount` 通知を46回から1回に削減した。社員は2行解除時の通知を3回から1回に削減した。商品再読込はページのコレクションリセットを2回から1回に削減した。各数値は行変更とコマンド完了の通知数に基づき、変更後は回帰テストで確認した。
- 売上は追加の2,048件の専用データでも確認した。`SalesManagementChecks --benchmark-isolated` で管理者と営業の月次件数・金額を独立したSQL集計と照合し、両方とも21回の測定で4回の `SELECT` だった。

## 実装と確認

| 対象 | ボトルネック | 対応と変更箇所 |
| --- | --- | --- |
| ログイン | 接続確認の同期 I/O、接続失敗時の500 msの待機、パスワード検証のCPU処理が UI を占有 | `F_login.xaml`、`F_login.xaml.cs`、`Presentation/LoginViewModel.cs`、`BusinessService.cs`。接続と認証を非同期化し、待機中の二重送信を防止。ログイン画面を閉じる際に処理をキャンセルする。 |
| 注文一覧 | ヘッダーと商品・注文の関連行を取り込み、受注明細のグループを注文ごとに再走査 | `ChumonManagementViewModel.cs`。行数、数量、保存金額を SQL で集計し、画面用の列だけを取得。明細なし、保存金額なし、所属営業所を含めて検証する。 |
| 売上一覧 | 認可済み一覧と別に月間件数・金額を取得 | `SalesService.cs`。同じ売上一覧に含まれる集計済み伝票金額を再利用。月末境界、管理状態、営業所範囲を検証する。 |
| 履歴一覧 | 単一の履歴ソースでもページ用のキーとデータを2回取得 | `HistoryManagementService.cs`、`HistoryManagementView.xaml.cs`。単一ソースは時刻とIDの順で直接ページを取得。複数ソースの場合はキーをSQLで結合してページングする。 |
| 顧客・商品・社員 | 一括選択・解除の途中で通知を繰り返し、バインディングが件数やボタン状態を再評価。商品再読込は同じ一覧を2回更新 | `Presentation/CustomerManagementViewModel.cs`、`Presentation/ProductManagementViewModel.cs`、`Presentation/EmployeeManagementViewModel.cs`。一括操作の完了後に集計を一度通知。商品一覧の再評価を1回にした。 |
| 在庫一覧 | 絞り込み結果を保存する手段は既存CSV出力に限定され、チェックした行は指定できなかった | `InventoryManagementView.xaml`、`InventoryManagementView.xaml.cs`、`Presentation/InventoryManagementViewModel.cs`、`InventoryService.cs`。3つの保存範囲で同じ認可とCSV処理を利用。ストリーミング、キャンセル、一時ファイルを使い、正常終了後に保存先を更新する。 |

## モジュール別の監査所見

| モジュール | 確認事項 |
| --- | --- |
| ログイン | 初回の WPF リソースおよび EF モデルの初期化と DB 接続待ちを識別した。認証成功には従来どおり有効社員と有効役職の確認が必要。 |
| ホーム | `F_Main` はナビゲーション先を選択時に生成し、ホームはセッション情報とショートカットを表示する。 |
| 受注管理 | 一覧は SQL のページング、検索のデバウンスとキャンセル、行コンテナの再利用を使用する。受注CSV取込の照合と印刷開始時の再読込には個別計測の余地がある。 |
| 注文管理 | 一覧の投影と SQL 集計を変更。集計後の検索・並び替えはメモリ上で行う。 |
| 売上管理 | 営業所で絞った読み取り専用投影を使用。月次集計を一覧のデータから求める。年月や管理状態の検索は取得後に適用する。 |
| 在庫管理 | SQL 側の集計とページング、キャンセルと要求の同一性確認、結果ページの一括差し替えを使用。新しい保存ボタンも検索更新中の旧ページを対象にできない。 |
| 発注管理 | 参照は範囲制限した投影を利用。明細検索の条件が一覧の一致件数に影響するため、SQL 側ページングへの移行には検索結果の比較が要る。 |
| 入庫管理 | 一覧の仮想化と読み取り投影を確認。入庫確定の更新は既存のトランザクションを使用。 |
| 出庫管理 | 関連データの取得は認可済みの注文範囲を SQL で利用する。出庫の確定と在庫更新は既存のサービスが担当する。 |
| 入荷管理 | ページの表示行を制限。商品や納品日を含む検索を SQL に移す場合、関連明細の条件も同じ結果になることを確認する必要がある。 |
| 出荷管理 | 認可済みの投影と行コンテナの再利用を使用。関連明細の検索を含む一覧には大規模データでの計測余地がある。 |
| 顧客管理 | 営業所範囲の取得と短いデバウンスを使用。一括選択・解除の通知を集約。 |
| 商品管理 | 商品コードとメーカーなどの既存条件を保持し、再読込と一括選択の通知回数を削減。 |
| 社員管理 | 認可された一覧をメモリ内でページング。ページを離れる際の選択解除と一括解除で集計通知を集約。 |
| 履歴管理 | 認可とタブ件数取得を共通化。全件タブは混在する履歴を時刻、ソース、IDで順序付けする。 |
| 設定・アカウント設定 | パスワード変更の同期DB処理とハッシュ計算は追加の計測対象。 |
| PDF・CSV・印刷 | 受注と発注は文字を含むWPF帳票をページ分割し、Windowsの印刷経路を使用。在庫CSVは検索結果をストリーミングし、安全な書き込みを共通化。 |
| 共通UI・サービス・DB | リソース辞書を共有し、画面終了時に対象のページを破棄して履歴イベントを解除する。実行時のライト／ダーク切り替え機能は見つからなかった。 |

## 検証範囲と引き続き測定が必要な項目

- WPFソリューションは実行中のアプリと分けた出力先でビルドした。コンパイラの警告とエラーはともに0件だった。
- 受注更新のWPF・入力チェック592件と、下書きを含む専用データベースのチェック277件が通過。受注非表示と認証のスイートは277件が通過し、権限、監査、ロールバック、同時実行、旧パスワードのハッシュ移行を確認した。出庫確定は再実行時に在庫と後続レコードを再更新しないことを確認した。
- 顧客50件、商品63件、社員52件、履歴173件、売上31件、発注79件、入庫・出庫の画面52件、入荷47件、出荷40件の回帰チェックが通過した。受注一覧の印刷は2種類のページ寸法で0〜102件のページ分割を検証した。
- 在庫は直前のページをスクロールした後に絞り込んでも該当行だけ表示されることをWPFテストで確認した。保存は検索結果、チェック行、全件のCSV内容と、キャンセルおよび権限拒否を専用データベースで確認した。Windows の保存先ダイアログと実ファイルの上書きは手動操作で未検証。
- 実データ規模でのSQL実行計画、物理インデックスの効果、長時間利用時のメモリ保持、連続ナビゲーションと全一覧のスクロール遅延、物理プリンターへの出力は今回の実測範囲外。
- 在庫の保存形式は UTF-8（BOM付き）CSV。チェック行は現在のページが対象。
